# Database Schema Validation

## Why This Matters

**The Problem We Had:**
- SQLAlchemy models had columns defined
- Database schema was missing those columns
- No automated checks caught this mismatch
- Applications failed at runtime with "column does not exist" errors

**How It Should Work:**
1. Developer updates SQLAlchemy model
2. Developer creates Alembic migration: `alembic revision --autogenerate -m "description"`
3. Developer applies migration: `alembic upgrade head`
4. Automated checks verify everything is in sync

## Automated Validation Layers

### 1. Pre-Commit Hook (Local Development)
Runs before every git commit to check schema sync.

**Setup:**
```bash
# Install pre-commit
pip install pre-commit

# Install hooks
pre-commit install

# Now every commit checks schema sync automatically
git commit -m "Add new column"
# ✅ Check Alembic Schema Sync.............................Passed
```

### 2. CI/CD Pipeline (GitHub Actions)
Runs on every pull request and push to main.

**Location:** `.github/workflows/schema-check.yml`

**What it does:**
- Spins up PostgreSQL with PostGIS
- Runs all migrations: `alembic upgrade head`
- Verifies sync: `alembic check`
- Fails if schema is out of sync

### 3. Manual Check Script
Run anytime to verify schema sync:

```bash
cd backend
python check_schema.py
```

Output:
```
✅ Database schema is IN SYNC (revision: 376fc70067b9)
```

Or:
```
❌ Database schema is OUT OF SYNC!
   Current database revision: 8740c54ea738
   Latest migration revision: 376fc70067b9

   Run: alembic upgrade head
```

### 4. Container Startup Check (Optional)
Add to backend startup to fail fast if schema is wrong:

```python
# In backend/app/main.py
from backend.check_schema import check_schema

@app.on_event("startup")
async def verify_schema():
    if not check_schema():
        raise RuntimeError("Database schema is out of sync! Run: alembic upgrade head")
```

## Workflow for Model Changes

### Adding/Modifying Columns

1. **Update SQLAlchemy Model**
```python
# backend/app/models/flight_logs.py
class FlightLog(Base):
    # ... existing columns ...
    new_column = Column(String(100))  # Add new column
```

2. **Generate Migration**
```bash
cd backend
alembic revision --autogenerate -m "Add new_column to flight_logs"
```

3. **Review Migration**
```bash
# Check the generated file in backend/alembic/versions/
cat backend/alembic/versions/*_add_new_column*.py
```

**⚠️ IMPORTANT:** Review autogenerated migrations! They can:
- Try to drop columns (if Alembic misdetects)
- Shrink varchar columns (data loss!)
- Remove indexes incorrectly

4. **Apply Migration**
```bash
alembic upgrade head
```

5. **Verify**
```bash
alembic check
# Should output: "No new upgrade operations detected."
```

6. **Commit**
```bash
git add .
git commit -m "Add new_column to flight_logs"
# Pre-commit hook will verify schema sync ✅
```

## Troubleshooting

### "Target database is not up to date"
```bash
# Apply missing migrations
alembic upgrade head

# Verify
alembic check
```

### "Column already exists" Error During Migration
The migration is trying to add a column that's already there (added manually).

**Solution:**
```bash
# Mark migration as applied without running it
alembic stamp head
```

### Autogenerated Migration Looks Wrong
Alembic's autogenerate can make mistakes. Always review!

**Common issues:**
- Tries to drop columns (Alembic thinks they were removed from model)
- Changes varchar(50) → varchar(20) (data loss!)
- Removes indexes that still exist

**Solution:** Manually edit the migration file before applying.

### Database Out of Sync After Manual SQL
If you ran manual SQL (like `ALTER TABLE ADD COLUMN`):

1. Generate migration to capture current state:
```bash
alembic revision --autogenerate -m "Sync manual changes"
```

2. Review migration - it should match your manual changes

3. Apply it:
```bash
alembic upgrade head
```

## Best Practices

1. **NEVER manually modify database schema** unless absolutely necessary
   - If you must, create a migration immediately after

2. **ALWAYS review autogenerated migrations** before applying
   - Check for accidental drops or type changes

3. **Run `alembic check` before commits**
   - Pre-commit hook does this automatically

4. **Test migrations on development first**
   - Never apply untested migrations to production

5. **Create backups before migrations**
```bash
./scripts/backup_database.sh
alembic upgrade head
```

6. **One migration per logical change**
   - Don't combine unrelated schema changes

## Integration with Docker

### Local Development
```bash
# Migrations run automatically on container start
docker compose up

# Or manually
docker compose exec backend alembic upgrade head
docker compose exec backend alembic check
```

### Production Deployment
```bash
# 1. Backup database
./scripts/backup_database.sh

# 2. Apply migrations
docker compose exec backend alembic upgrade head

# 3. Verify
docker compose exec backend alembic check

# 4. Restart services
docker compose restart backend celery
```
